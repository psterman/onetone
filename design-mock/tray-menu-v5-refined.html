V1 暴露的 9 个问题

"现在能用吗" 答 "能 · 语音 + 软键盘 监听中"
问句 + 答 3 件事混在一行
用户问的是"能不能用"，回的是"能"+"哪些通道"+"状态"。一句回答里塞 3 个判断。
toggle 行 = [运行中, 麦开, 按键]
"运行中"是状态不是 toggle
"运行中"是个状态显示，不是操作；和另外两个真 toggle 混在一起，按钮含义不清。
3 个 toggle 不对应下面 4 通道
"按键"toggle 不知道切的是什么
上面 3 按钮、下面 4 通道，缺少一一对应——"按键"按钮是停用按键通道？还是切触发方式？
4 通道 = 4 个 70px 宽的小方块
信息密度太低
只够塞"语音·Vosk"这种缩写，看不到上次触发、引擎状态等关键信号。
"2s 前"在 hero，"4s 前"在最近事件
两个时间点不知道哪个最新
时间线混乱，应该只有 1 个权威时间戳。
"麦开"和"按键"toggle 平级
麦静音是隐私最高优先级，应该独立
静音是 vibecoder 进会议/通话唯一要切的操作，识别度不够。
最近事件 1 行小字
无结果（已发送/未发送/失败）
vibecoder 最关心"刚才那句有没有被处理"——必须看到 outcome。
"Vosk"只显示引擎名
无引擎健康（已就绪/加载中/失败）
唤醒失败 90% 来自引擎没准备好，这是排错最高频信号。
"退出"在 footer 跟"主窗口"挨着
误触风险
退出不该是 1-click 邻接操作。挪到角落小图标，降级为半透明。

V5 的 9 个对应改动

V1: "现在能用吗" → "能 · 语音+软键盘 监听中"
V5: hero 大字"监听中" + 3 个激活通道 chip
去掉问句，状态直接说人话；激活通道变成 chip 形式，一眼看清"哪些在跑"。
V1: toggle 行 = [运行中, 麦开, 按键]
V5: hero 右侧大按钮 = [暂停]（唯一的全局动作）
"运行中"是状态不是操作；只保留"暂停/继续"作为 hero 上的全局动作，颜色编码（蓝/橙）。
V1: 3 toggle 和 4 通道不对应
V5: 4 通道 = 4 行，纵向可点
每行 = 1 通道 1 行 = 1 状态 + 1 详情，右侧 chevron 跳主页深链。一一对应，可达性清晰。
V1: 4 通道挤成 70px 小方块
V5: 4 通道纵行，每行 2 行文字
第一行 = 名称 + 状态点；第二行 = 关键值（如"Vosk·已就绪·唤醒词…""HID_R03·双击·3s 前"）。
V1: "2s 前"和"4s 前"重复
V5: 唯一时间戳 = 最近事件卡片的"刚才 2s 前"
所有"时间"语义都聚到"刚才事件"这张卡里，hero 不再背时间。
V1: "麦开"只是 toggle 行的一个
V5: 麦静音独立成 1 行（蓝色高亮 + 物理 toggle）
隐私最敏感操作，单独成行。蓝色 = 正常，红色 = 静音，状态色 + 物理 toggle 一目了然。
V1: 1 行"打开 main.rs · 4s 前"
V5: event-card = 通道 icon + 文字 + outcome chip
vibecoder 最关心"刚才那句有没有被处理"——outcome chip 显式标"已发送 / 未发送 / 失败"。
V1: 通道只显示引擎名"Vosk"
V5: "Vosk · 已就绪 · 唤醒词"
明确显示引擎健康度（已就绪 / 加载中 / 失败），这是排错最高频信号。错误时变红字。
V1: "退出"和"主窗口"挨着
V5: "退出"挪到 footer 角落，半透明小图标
降低误触权重。主窗口+设置+诊断 = 平等 3 个入口；退出 = 视觉降级的"危险操作"。

架构影响

V5 的 UI 改动直接对应后端状态模型的重构。下面是 v1 → v5 状态模型和 IPC 的差异。

1 状态模型：从 70 字段平铺 → 4 段结构

V1: 70 字段平铺（paused / triggerKey / engine / mic / agent / schemes / modes / last_event_text / target_text / repair_text ...）
V5: 4 段结构
TrayState { global: { mode, reason?, pulse_color, active_channel_ids[] }, mic: { available, muted, device, level }, channels: ChannelSummary[], // 固定 4 项：voice/keys/softPad/camera event: { t, channel, text, outcome } | null, deep_links: DeepLink[] }
V5 整个 UI 由这 4 段渲染。tray 完全不知道 habit/setting 页面存在。

2 数据流：轮询 → 事件总线

V1: 2 秒全量轮询 + __tray_patch__ 整树重绘
V5: 4 段独立订阅 + JSON diff patch
tray_state.subscribe(seg, callback) → MicMuted → only patch .mic segment → ChannelChanged(id) → only patch that row → LastEvent → only patch event card
每个段独立订阅；状态变化只 patch 受影响段，不再整树重绘。

3 前端组件：tray-menu.html 单文件 → 4 个组件

V1: 18KB 单文件，3 个 render 函数（main/schemes/modes）手写 DOM
V5: 4 个 Web Component
<tray-status-hero state={global} onPause={...} /> <tray-event-card event={event} /> <tray-channel-row channel={ch} onOpen={...} /> <tray-mic-toggle mic={mic} onToggle={...} />
每个段 1 个组件，单向数据流；加新段 = 加组件，不改 shell。

4 事件总线：复用现有 ActivityBus

V1: 重新造轮子，每个事件单独发布
V5: 复用 home 已有 ActivityBus
// home 已经有 window.ActivityBus.emit({ ch, text, status, t }) // V5 只需加 1 个新订阅点 ActivityBus.tail(1).subscribe(e => { patch_event_card(e) })
不引入新机制，tray = ActivityBus 的另一个订阅者。和首页状态自动同步。
