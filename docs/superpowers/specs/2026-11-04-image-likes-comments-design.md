# 图片站点赞 + 按图评论 设计文档

日期：2026-11-04
状态：待用户审阅
范围：`daily-image-site` 的图片点赞功能，以及「评论跟图走」的留言板扩展
约束：不新建任何 Cloudflare 资源（复用现有 R2 binding 与 Pages Functions）；不改构建链路；不引入前端依赖

---

## 1. 目标与非目标

### 目标

1. 读者能对**单张图片**点赞，并看到每张图的赞数。
2. 读者能对**单张图片**发表评论，评论和图绑定在一起（不是又一条飘在总留言板上的文字）。
3. 评论继续受投稿口令保护；点赞不需要口令（点一下就完事）。
4. 不影响现有链路：manifest 仍是静态文件，构建流程不变，留言板老数据不受影响。

### 非目标（本期不做）

- 不做点赞排行榜 / 热图页。
- 不做回复评论（楼中楼）、不点赞评论。
- 不做图片上传、不做用户账号系统。
- 不做分享/转发计数。
- 不改 R2 图片的存储与出图方式。

## 2. 现状盘点（设计依据）

### 2.1 能直接复用的

| 能力 | 位置 | 复用方式 |
|---|---|---|
| R2 存储 + etag 乐观锁 | `functions/board/api.js` 的 `readJson` / `writeJson` / `mutate` | 几乎逐段照搬到新函数 |
| IP 哈希限流 | 同上 `checkRate` / `recordHit` | 同一套滑窗逻辑，换阈值与存储键 |
| Origin 防 CSRF | 同上 `sameOrigin` | 原样照搬 |
| 作者令牌只存哈希 | 同上 `sha256hex('board-author-v1|' + token)` | 点赞沿用同样的「客户端持令牌、服务端只留哈希」 |
| 投稿口令鉴权 | `functions/board/_middleware.js` | 评论直接走这条，不改 |
| 留言板存储 | R2 `board/messages.json` | 加三个可选字段，不新建对象 |
| 前端图片卡片 / 全屏查看器 | `site/app.js` 的 `renderTab` / `openViewer` / `renderViewer` | 在既有 DOM 上挂角标与操作栏 |

### 2.2 真正的三个难点

**难点一：单图键必须是「日期 + 栏目内序号」的复合键。**
manifest 里的 `id` 形如 `jianwen_001`，只是**栏目内序号**，不含日期 —— 每一期都有 `jianwen_001`。直接拿它当存储键，不同期的点赞会互相串。
→ 存储键一律用 `<日期>/<栏目>_<序号>`，落地成「一期一个文件」，天然不撞。

**难点二：243 张图的计数不能一图一请求。**
每张图发一次请求就是 243 个请求，页面直接卡死。
→ 一期一个聚合文件，页面加载**一次**请求拿全部计数，再写回 DOM。

**难点三：位置编号作键的已知错位风险。**
`jianwen_001` 是位置编号，删一张图后面全部前移。已发布的期次 manifest 是冻结的，所以日常没问题；但「发出去之后又删图重发」会让序号前移，旧的点赞/评论挂到隔壁图上。
→ 本期接受该限制并写进 README（详见 §7）。

## 3. 数据模型

全部落在现有 bucket `daily-images`，用前缀隔开。

### 3.1 点赞：`likes/<日期>.json`

```json
{
  "counts": { "jianwen_001": 3, "jianxiao_012": 1 },
  "voters": { "jianwen_001": ["9f2c1a7b3d4e5f60", "1a2b3c4d5e6f7a8b"] }
}
```

- `counts`：id → 赞数
- `voters`：id → 点过赞的访客哈希列表（去重依据）
- 访客哈希 = `sha256('like-voter-v1|' + vid).slice(0,16)`，**不存原始 vid**
- 一期一个文件 → 读一次拿全期计数；不同期天然隔离
- 单 id 的 voters 上限 500；**达到上限后该图拒绝新的点赞**（返回 409 + 「这张图点赞太多啦」），计数不再增加 —— 防止文件无限膨胀，也避免去重失效

### 3.2 评论：复用 `board/messages.json`

每条留言新增三个**可选**字段：

```json
{
  "id": "…", "ts": 1750000000000, "name": "…", "body": "…",
  "link": "", "cat": "",
  "imgDate": "2026-11-03",
  "imgId": "jianxiao_012",
  "imgThumb": "/img/2026-11-03/jianxiao/ab12cd34ef_012_t.webp",
  "author": "<hash>"
}
```

- 三个字段要么都不给（普通留言），要么都给且都合法
- 老留言没有这些字段 → 前端按普通留言渲染，**零影响**
- `imgThumb` 是站内相对路径，**不是**任意 URL

### 3.3 限流计数：`likes/rate.json`

结构与 `board/rate.json` 一致（`{ hits: [{ts, ip}] }`），保留窗口 2000 条。

## 4. 接口契约

### 4.1 `GET /likes/api?date=YYYY-MM-DD`

访客无关的只读数据，**可被边缘缓存**。

```json
{
  "ok": true,
  "date": "2026-11-03",
  "counts": { "jianwen_001": 3 },
  "comments": { "jianxiao_012": 2 }
}
```

- `counts`：该期每张图的赞数（没有赞的图不出现）
- `comments`：该期每张图的评论数（从 `board/messages.json` 按 `imgDate` + `imgId` 分组统计）
- **不含访客相关字段** —— 这是它能被边缘缓存的前提（见 §6.3）
- `date` 缺失或格式非法 → 400；该期还没有任何点赞 / 评论时返回空的 `counts` / `comments`（不报错）

缓存头：`Cache-Control: public, max-age=30` + `ETag`。30 秒后自然过期；本项目 API Token 没有 Cache Purge 权限（实测 401），所以不做主动失效。

### 4.2 `POST /likes/api`

请求头 `x-daily-visitor: <16 位 hex>`；请求体：

```json
{ "date": "2026-11-03", "id": "jianxiao_012", "on": true }
```

响应：

```json
{ "ok": true, "id": "jianxiao_012", "count": 4, "on": true }
```

语义**幂等**：`on` 表达目标状态，不是「翻转」。重复提交同一个 `on` 不会二次累加。

处理顺序：限流 → 读文件 → 校验 vid 是否已在 voters → 按 `on` 增删 → etag 条件写回 → 记录限流命中。
返回的 `count` 是写入后的真实计数（若因并发重试，客户端以返回值为准）。
该期点赞文件还不存在时自动创建（`mutate` 的 fallback 路径）。

### 4.3 `POST /board/api`（扩展）

在现有载荷上接受三个可选字段，校验规则：

| 字段 | 正则 | 不合法时 |
|---|---|---|
| `imgDate` | `^\d{4}-\d{2}-\d{2}$` | 400 |
| `imgId` | `^[a-z]{3,10}_\d{3}$` | 400 |
| `imgThumb` | `^/img/\d{4}-\d{2}-\d{2}/[a-z]+/[0-9a-f]{10}_\d{3}_t\.webp$` | 400 |

三个字段要么都不给，要么都给（给了 `imgDate` 却没给 `imgThumb` 也算 400）。`imgThumb` 的白名单是关键 —— 它会被渲染成 `<img src>`，放开就等于允许任意 URL 注入。

`GET /board/api` 的响应项增加 `imgDate` / `imgId` / `imgThumb` 三个字段（没有就是空字符串）。

### 4.4 留言板页的图上下文

`/board/?img=<日期>&id=<栏目_序号>&thumb=<缩略图路径>`

- 三个 query 参数齐全才进入「按图过滤」模式，否则当普通留言板
- `thumb` 走与 §4.3 相同的白名单校验，不合法就忽略该参数
- 页面顶部显示目标图缩略图 + 日期 + 栏目序号；列表默认只显示这张图的评论；旁边给「看全部留言」链接（`/board/`）

## 5. 前端交互

### 5.1 访客 ID

- 首次使用时生成 16 位随机 hex，存 `localStorage['like-vid-v1']`
- 只在点赞时随 `x-daily-visitor` 头发给服务端
- 「我赞过哪些图」由**本地**记录：`localStorage['like-mine-v1'] = { "<日期>": ["jianxiao_012", …] }`
- 换手机 / 清缓存 → 重置（本期明确接受的语义）

**为什么 `mine` 不从服务端取**：访客相关的响应不能被边缘缓存，否则会把一个人的点赞清单发给别人。本地记录让 GET 响应保持访客无关，从而可缓存。

### 5.2 缩略图角标

- 页面加载时拉一次 `/likes/api?date=<日期>`，把 `counts` 写进每张图对应的 cell
- 角标渲染在格子右上角，**只在赞数 > 0 时显示**（0 赞不显示，避免 243 个角标糊满屏）
- 角标**只显示、不可单独点击**（`pointer-events: none`），点它跟点格子一样打开查看器 —— 手机上小角标容易误触，不做成点赞按钮
- 角标内容形如 `👍 12`

### 5.3 全屏查看器操作栏

底部加一条操作栏（flex，两个大点击区，命中区 ≥ 44px）：

```
[ 👍 12（点我赞） ]   [ 💬 2 条评论 · 评论这张图 ]
```

- 点赞按钮：`x-daily-visitor` 已在 localStorage；POST 成功后用返回的 `count` 更新，并写入本地 `mine`
- 已赞过的图，👍 变成实心/高亮态
- 「评论这张图」→ 跳 `/board/?img=…&id=…&thumb=…`

### 5.4 留言板页

- 从图片页跳过来时：顶部显示目标图（缩略图 + 「2026-11-03 · 见笑 #12」），列表只显示这张图的评论
- 普通留言与带图留言混排时，带图的显示缩略图（可点击跳回那张图）
- 「看全部留言」链接清掉过滤

### 5.5 微信兼容

- 角标：绝对定位 + `pointer-events: none`，不影响既有的 IntersectionObserver 懒加载队列
- 查看器操作栏：纯 flex + 安全区内边距，不用 `position: fixed` 叠加
- 不引入任何新依赖，不用 `srcset`，不改变既有 viewport 写法
- 全部 `fetch` 为同源，无需 CORS

## 6. 安全与防滥用

### 6.1 鉴权矩阵

| 动作 | 访问口令（GATE_TOKEN） | 投稿口令（SUBMIT_TOKEN） | 说明 |
|---|---|---|---|
| 看图 | 跟随全站设置 | — | `/img/*` 已由根 `_middleware.js` 保护 |
| 看点赞数 / 评论数 | 不要求 | 不要求 | 只有计数，不暴露图片本身 |
| 点赞 | 不要求 | 不要求 | 开放，靠限流防刷 |
| 发表评论 | 不要求 | **要求** | 沿用 `dboard` cookie |
| 看留言 | 不要求 | 不要求 | 页面公开是刻意的 |

点赞接口**不与访问口令联动**：它只暴露计数，不暴露图片内容。若日后要把它也锁进访问口令，改动是根 `_middleware.js` 里加一条路径判断。

### 6.2 限流（按 IP 哈希，不存原始 IP）

| 动作 | 1 分钟 | 1 小时 |
|---|---|---|
| 点赞 | 30 次 | 300 次 |
| 评论 | 3 条 | 20 条（沿用现状） |

点赞阈值比留言宽得多 —— 点赞本来就在连着点，但仍然要挡住「一个人刷几千张图」。

### 6.3 缓存安全

`GET /likes/api` 的响应**不得包含**访客相关字段，否则边缘缓存会把一个访客的点赞清单发给所有人。访客状态一律走本地存储。

### 6.4 其他

- 所有写入校验 `Origin`（防跨站 POST）
- 所有用户输入用 `textContent` 插入，不拼 HTML
- `imgThumb` 白名单正则（同 §4.3）
- 点赞与评论的写入都走 etag 条件写，并发不会互相覆盖

## 7. 已知限制与取舍

| # | 限制 | 影响 | 为什么本期不改 |
|---|---|---|---|
| 1 | **单图键是位置编号**（`jianxiao_012`）。发布后若再删图重发，序号前移，旧点赞/评论会挂到隔壁图上 | 轻微（显示错位，不丢数据） | 根治要把源文件名写进 manifest，而 build 有「从源图构建」和「源图被删后从已转码产物重建」两条路径，后者拿不到源文件名；为低概率场景改构建并重发 10 期，性价比不高 |
| 2 | **计数最多滞后 30 秒** | 轻微 | API Token 没有 Cache Purge 权限（实测 401），无法主动失效边缘缓存 |
| 3 | **留言板全局 500 条上限不变** | 按图评论多了更快触顶 | 加大上限要重新考虑存储结构，本期不动 |
| 4 | **换设备点赞会重置** | 轻微 | 用户明确选择 |
| 5 | 单 id 的 voters 上限 500 | 极少数热门图可能超 | 防文件无限膨胀 |
