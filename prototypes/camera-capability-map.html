摄像头能做什么

这一页不给你表单，先把三件事说清楚：摄像头能感知什么、它能驱动哪些动作、 以及这些动作和按键、语音、软垫是同一套。看懂这三件事，才知道该往哪配。

能驱动哪些动作

9 个
还有一组应用内动作（遮罩、暂停语音、自动静音、光标跟随…），不走上层路由，由摄像头自己执行。
🔗 最关键的一件事

这 9 个动作不是摄像头专属。按键、语音、软垫触发的是同一组动作。所以「摇头 → 中断 Agent」和「按某键 → 中断 Agent」最终效果完全一样，只是触发方式不同。

🛡 有 2 个动作摄像头不能自己完成

完成并发送和批准触发后只会进入「等待确认」，必须你用按键或语音再确认一次。这是防止摄像头误发内容、误批操作的保护，关不掉。

🚫 另外 16 个动作摄像头绑不了

比如「暂停听写」「打开应用」「向 Agent 发继续」——这些只开放给按键/语音/软垫。原因和完整清单见跨通道矩阵页。

关于「应用内动作」和「语义动作」的区别： 前者（遮罩、暂停语音、自动静音、光标跟随）是摄像头自己完成的小动作，执行快、不走统一路由； 后者（开始听写、取消本轮、中断 Agent…）走的是和按键、语音、软垫共用的统一动作层，所以能和其他通道组合使用。 套用方案时两者可以混着来。

✅ 直执路径（7 个安全动作）

摄像头识别 → 路由 → 判定 → 直接执行。全程无感，不打断你。

离席→路由→ 直接执行·取消本轮
⏸ 等待确认路径（2 个危险动作）

摄像头识别 → 路由 → 生成待确认项 → 等你用按键或语音确认 → 才真正执行。摄像头不能自己确认。

长眨→待确认→ 你按一下→才发送
摄像头自己确认← 被禁止
为什么摄像头不能自己确认？ 因为「完成并发送」会把内容发出去、「批准」会放行操作——这两件事一旦误触，代价不可逆。 所以摄像头只能提出请求，不能自己拍板。这条约束是写死在代码里的，任何 UI 都不应该让它看起来可以绕过。
组合能力： 因为四个通道走同一条路，你可以自由混搭—— 比如「挥手 → 隐藏面板」（摄像头），同时「按某键 → 打开应用」（按键），两者互不干扰。 甚至同一个动作被多个通道绑定也很正常，比如「摇头 → 取消本轮」和「拍某键 → 取消本轮」同时存在，效果一样。

💡 怎么用这张表

看到摄像头能用的动作 → 配成规则；看到只能用语音的 → 就用语音做。四个通道是互补的，不是竞争关系。摄像头强在「无意识状态感知」（人走没走、在不在看），语音强在「有意识的内容输入」。

🔧 发现一个配置错误

现有预设把摄像头绑到了 onetone.resume，但该动作的 channels 不含 camera。这条规则能存进配置却永远不执行，建议修掉——要么换成应用内 resumeVoice，要么把 resume 开放给 camera。
