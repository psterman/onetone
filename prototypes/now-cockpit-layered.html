为什么这样分层：首页的读者是「正在干活的我」，诊断页的读者是「想搞清楚的我」。 同一份数据，两种呈现密度。不删数据，只挪位置。

四层：用户只碰第一层

这是整个设计的核心约束。下面三层越复杂越好用，但它们不能漏到第一层。

1 Now 首页 情景名 + 正在帮你 + 调整  ·  用户语言，无技术词
2 Effective Habit Resolver pin › override › auto 跟前台 › baseline
3 Context Evidence 前台应用 · 代码库状态 · Agent 等待 · 摄像头 presence
4 Sensors Camera · Keyboard · Window · Agent Hook

这版和前两版的差别

版本首页形态问题
第一次「我看到的你」+ 能力全景营销化：编的文案，且把监控感摆在第一屏
第二次应用名 + 承诺列表还是编的：承诺来自通用 assists 数组，跟应用无关
第三次纯字段表（Resolver / slot / status）工业化：把推理过程摊给用户，像调试工具
这次情景 + 真实 action 名 表面是用户语言，底层是真实字段，复杂部分收进 ⓘ 和诊断
三次修改的共同教训：数据和体验不是二选一。

第一次我为了体验牺牲了真实性（编文案）； 第三次我为了真实性牺牲了体验（摊字段）。

正确做法是分层：第一层用真实数据做用户友好的投影， 下面几层保持完整，需要时用 ⓘ 展开或去诊断页。
仍然存在的缺口（不影响本层，但影响下一层）：
  1. 情景名还是技术串——需要 MappingEntry.displayName 字段让用户起名
  2. 「可能正在」算法没有——suggested 恒 false
  3. 摄像头未接入——presence 恒 Unknown
  4. assists 存中文——但改成分层后它不再是主角，优先级下降
