这版和现状的差别：现状首页是「今天做了什么 + 我的情景 + 需要决定」—— 证明了它「做了什么」，但没解释它「怎么理解你」。 补上 A 和 B 之后，链路才闭合：看到你 → 做了什么 → 为什么这么做 → 靠什么知道。

三块分别解决什么

A、B、C 的性质完全不同：A 和 B 是用户可感知的产品能力，C 是工程透明层。不能混为一谈。

A 我看到的你

回答「它怎么理解我」。这是 Context Engine 的门面，也是整个状态中心的核心表达。

关键设计：最后一行我选择画成「不知道」而不是画成「你在电脑前」。 ContextSnapshot.resolver.rs:170 的规则是「缺证据就不给结论」—— UI 必须诚实反映这一点，否则整个「它真的懂我」的叙事就塌了。

B 因果链

回答「它刚才为什么这么做」。这是自动化软件和普通脚本的区别——普通脚本不解释自己。

步骤数据来源状态
① 事实entry.detail字段有，值缺
② 交叉验证需要多源同时刻快照需新建
③ 判断ContextSnapshot 仲裁结果已就绪
④ 动作ActionHistoryEntry已就绪
B 是三块里最贵的。②「交叉验证」需要同一时刻的多个源快照—— 而现在各源是各自 emit 的，没有统一时间点。这要求在 Context 层加「冻结快照」能力。 建议 A 做完再评估 B。

C 工程状态（不可见层）

C 不在首页，在设置里。它解决的是「我不信你」——把每个来源能知道什么、不能知道什么摊开。

C 的判据：每一行都要能回答「它凭什么这么说」。 摄像头那行写「画面只在本机处理，不上传」——不说这句，用户就不敢开。 我在下面列了每行的隐私边界，这部分不能省。
