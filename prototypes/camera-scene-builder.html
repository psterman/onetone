摄像头 · 方案三 交互原型 · 数据取自 semantic.rs 权威目录

现状两版都在做「设置页」——让人逐项勾选。但用户真实的心理是「我想让摄像头替我做一件事」。 方案三改成「自动化构建器」：先选场景（什么时候），再配规则（做什么），动作从库里挑，且只显示摄像头真能绑的。

① 两版各自的问题 对着截图逐条说

Camera 2 · 场景能力

方向对，但没落地

  • 「接任务 / 按钮发」是双轨概念，用户不知道区别，也不知道该选哪个
  • 分类芯片只是计数不是导航——离开座位2 / 开会1 / 手势2 / 视线，点进去没有预期
  • 左侧仅 2 条规则，右侧 60% 全是空白，重心严重失衡
  • 「别丢即使用中」「在列表 = 使用中」这类元信息抢占注意力
  • 关系搞反了：离席/回席本身是「信号」，却被当成场景下的「类规则」
Camera 1 · Pro 确认与安全

典型的设置页思维

  • 10 个平级子标签零优先级，用户得记住每格放了什么
  • 每行是「开关+长描述+动作下拉+时长下拉」控件墙，主任务被稀释
  • 描述被截断（"故意闭眼不算。故意闭眼达到「闭眼多久」所选秒数…开启「响…"）
  • 动作下拉是裸的「不执行动作」，用户根本不知道能选什么
  • 美颜 / 久坐 / 移窗 与 离席 / 握手 同级，性质完全不同
共同根因

两版都在犯同一个错

  • 都是静态设置页，不是自动化构建器
  • 都没回答进门第一个问题：「摄像头能感知什么 / 能驱动什么」
  • 都没把适配与校准（前置条件）当一等公民
  • 都把设备参数和规则混在同一层

③ 方案三的四个关键改动

改动 1

主轴换成「场景」

用户想的是「开会的时候 / 我离开的时候」，不是「离席 / 回席 / 挥手」这些技术项。场景是用户脑中的时间切片，天然带上下文。

改动 2

动作库只给「真能绑的」

按 semantic.rs 的 channels 字段过滤，9 个可绑动作分组展示，2 个需二次确认的显式打标，不可选的明确列出原因。

改动 3

就绪度升为一等公民

眨眼需基线、视线需校准——这些前置条件常驻右栏，未就绪时对应规则直接置灰并给一键入口。用户不再遇到「为什么不准却找不到原因」。

改动 4

设备参数与画面观感移出

分辨率 / FPS / 抗闪烁收进「设备」抽屉；美颜 / 面具移出摄像头页——装饰不是摄像头的能力，混进来只会稀释主线。

    ⚠️ 信号尚未就绪

    感知库 摄像头能「看到」什么 · 8 个信号

    这是用户进门前应该先知道的事。关键改动：每个信号都标注就绪状态，未就绪的直接说清原因和前置动作。

    信号靠什么感知判定条件就绪状态说明
    离席人脸消失持续 ≥ 3 秒就绪离开座位的核心信号
    回席人脸回来持续 ≥ 1 秒就绪与离席成对，无需单独开关
    旁人出现第二张脸即时就绪只提醒，不自动遮罩
    摇头头部左右摆3 拍就绪瞬时动作，天然表达「不要」
    挥手手掌摆动数次就绪适合「等一下」
    故意眨眼闭眼保持0.6 / 1 / 1.2 秒需适配需先采集个人基线，否则无法区分普通眨眼
    视线看某屏视线方向估算停留 > 0.5 秒需校准需先做视线校准，未校准无屏幕坐标
    久坐超时在席时长20 分钟就绪纯计时，不需适配

    动作库 摄像头能「驱动」什么 · 按 semantic.rs 的 channels 字段权威过滤

    这是方案三最重要的一处修正：动作库只显示摄像头真能绑的，并把「绑不了」的原因说清楚，让用户知道边界在哪。

    🚫 摄像头绑不了（16 个）· 显式告知，而不是让用户猜

    动作语义 ID原因提示
    暂停听写 / 恢复语音input.pause onetone.pause/resume仅 按键·语音·软垫如果你需要「离席自动暂停」，走本地动作 pauseVoice（见下）
    完成本轮input.commit仅 按键·语音·软垫与 input.send 不同，不含发送
    打开应用 / 恢复布局app.open仅 按键·语音·软垫工作区布局可绑；单开应用暂不支持
    应用快捷键app.shortcut仅 按键·软垫—
    向 Agent 发「继续」agent.continue仅 按键·语音·软垫用 agent.focus + 语音更稳
    回答 Agent / 选选项 / 新建会话 等agent.respond choice.select session.new无 camera 通道这类需要「说什么」的动作用语音更合适

    另一处：本地动作 token（与语义目录并存的第二套词表）

    摄像头还有一组应用内本地动作，不走语义目录，但当前 UI 实际用的就是这组：
    privacyScreen 应用内遮罩 · pauseVoice 暂停语音 · resumeVoice 恢复语音 · pressEsc 语音取消 · pressCtrlI 语音输入法激活 · lowPowerMode 低消耗运行 · toggleOralListen 口头收听
    方案三的处理：保留这组能力（它确实可用），但在 UI 上与语义动作明确分区并统一中文命名，标注「应用内」， 用户不必再分辨「暂停听写」和「暂停语音」哪个是哪个。
