OneTone website：从 WorkBuddy 官网借鉴什么

不比较旧版 onetone.app。聚焦仓库最新源码，逐维度给出可落地的修改意见：值得借鉴的、是坑的、以及已经出现的错误与偏差。

0 · 先给结论

OneTone 的 demo 做得比 WorkBuddy 更精致，但"说服"做得比 WorkBuddy 弱得多。

WorkBuddy 靠三件事让人行动：一句话说清价值、把真产品摆到首屏、用数字和社会证明兜底。OneTone 目前把力气花在了"滚动叙事 + 动效"上，用户看完 4 个章节仍然不知道：这东西比系统自带语音输入强在哪、我要花几分钟、在我的 Cursor 里能不能用。

0首页量化指标
0首页可输入元素
0home-demo.js 点击监听
3/11功能页未进主导航
4生产环境 CDN 依赖

1 · 值得借鉴的（照着做）

1.1 Hero：从"口号"改成"一句话价值 + 一个数字"

现在（index.html）

H1「一声」+「想什么，说一声」+ 轮播「Cursor 里直接说」
正文：按一下侧键就能开麦。Cursor、Claude、Trae……在哪写就在哪说。

问题：H1 是品牌名不是价值；"在哪写就在哪说"很文艺但不含决策信息。

WorkBuddy 的做法

「我帮你 / 做设计」→ 3 字 punchline
一句 60 字内价值：WorkBuddy 是腾讯出品的全场景 AI 办公工作台。说出要求、开始执行任务、交付完整成果。

可迁移：一句话同时回答"是什么 + 给我什么"。

落地建议

  • H1 改成动作 + 结果：按一下侧键，开口写代码
  • 副标题塞进一个数字：3 分钟装好，在你已经在用的 Cursor / Claude / Trae 里直接说。Windows 10/11。
  • 把「适用于 Windows 10/11」「macOS 开发中」这个胶囊保留，但加上免费用、开源——vibecoding 用户最怕的是"又一个要订阅的"。

1.2 把"动画"升级成"产品演示壳"

WorkBuddy 首屏下方放的不是动画，是真实 App 外壳：侧边栏 tabs（新建任务/专家/技能/连接器/自动化）、任务时间线、最终产物（.md / .docx / .pptx）。用户 5 秒就"看懂"了产品。

落地建议（改造现有 hero demo，不重写）

现在 #opDemo 已经有应用窗口 + 设备 SVG 的底子，缺的是"任务完成"的闭环。建议把它改成一条完整的因果链：

  • 左上：目标 App 标题栏显示 Cursor — main.tsx（现在是抽象的 "Target App Editor"）
  • 左中：光标停在空行上
  • 右：按下鼠标侧键 → 声波起 → 顶部状态条「正在听…」
  • 回到左：文字逐字落到光标处
  • 底部状态条：已上屏 87 字 · 用时 6.4 秒 ← 这就是"数据"

关键：让 demo 有一个"完成态"，而不是无限循环。WorkBuddy 的演示之所以有效，是因为它演到了"交付"。

1.3 用"场景 tab"替掉一部分滚动章节

WorkBuddy 用「研究 / 文档 / 设计 / 开发」四个 tab + 短视频，把 4 个能力压进 1 屏。OneTone 现在用 4 个 100vh 章节讲「触发 / 摄像头 / 语音 / SoftPad」，需要滚 4 屏多。

落地建议

  • 把「摄像头」和「SoftPad」收进一个 可切换的场景区（tab 或左右分栏），保留 1 屏
  • 把「触发」和「语音」留在主叙事里——这是核心价值，值得展开
  • 预期效果：首页从 ~8 屏压到 ~5 屏，vibecoding 用户（普遍耐心低）更容易走到下载

1.4 给每个章节装一个"章节级 CTA"

WorkBuddy 每个场景块都有明确的下一步。OneTone 目前只有「绑定按键」「了解摄像头」等章节 chip，但缺少"现在就下载"的即时出口。

  • 在每个 .chapter-copy 末尾增加一行：装好就能试 → 下载（约 30 MB）
  • 把 outcome-caption（结果说明）旁边加一个小的「去试试」链接

1.5 数据：补 4 个可信指标

WorkBuddy 用「15 分钟交付报告」这种具体数字建立预期。OneTone 全站零量化指标——这是最容易补、也最容易被低估的一块。

3 分钟从下载到说第一句话
1 个键接管任意语音输入法
11+已验证 Agent / IDE
~30 MB安装包 · 本地运行

注意：这 4 个数都来自现有素材（download.html 已提到 30 MB，品牌墙已有 11 个 logo），不需要编数据，只是把它们提到首屏。

1.6 Footer 结构化 + 社群触点

WorkBuddy footer 是 4 列（服务条款 / 文档指引 / 产品下载 / 联系我们）+ 二维码。OneTone footer 是「功能链接 + 法律链接」两坨。

  • 拆成 4 列：产品（语音/按键/摄像头/SoftPad）、上手（快速上手/常见问题/更新日志）、开源（GitHub/反馈问题/支持项目）、法律
  • 加一行版本号 v1.x.x——vibecoding 用户会看这个判断项目活不活跃

2 · 不要照抄的（WorkBuddy 的坑）

WorkBuddy 的做法为什么对 OneTone 是坑应该怎么做
坑4 档定价 + 划线价 + 限免 OneTone 是免费开源小工具。放定价会让 vibecoding 用户第一反应变成"这要钱吗？"，反而抬高门槛。 在 hero 直接写死 免费 · 开源，比放一张定价表更有说服力。
坑30+ 客户 logo 墙 logo 墙是"已有规模"的证明。独立项目硬摆一排 logo，没真实客户时反而显得心虚。 用现有素材替代：GitHub stars 数、下载量、V2EX/社区讨论截图。有 1 个真实数字胜过 30 个借来的 logo。
坑「打通腾讯生态」 这是腾讯的自有优势，OneTone 没有等价背书，照抄结构会露怯。 把生态墙的叙事从"我们跟谁合作"改成"你在哪写，就能在哪说"——即现有的品牌兼容墙，这个方向是对的，保留。
坑大量场景视频 视频制作+维护成本极高，小团队做一轮就停更，反而显得项目停滞。 继续用现有的 SVG/Canvas 交互 demo。这恰恰是 OneTone 比 WorkBuddy 强的地方，别丢。
坑「活动」「Nova 大使」运营栏目 没有运营人力时就是死链，且会稀释核心转化路径。 导航保持精简，不加运营栏目。
坑H1 放在 demo 内部 WorkBuddy 页面真正的 H1 是 demo 里的「AI 行业趋势深度研究报告」，价值主张反而不是标题——SEO 和无障碍都吃亏。 OneTone 现在 H1 是「一声」，建议改成价值句，这个别学 WorkBuddy。

3 · 已经出现的错误与偏差（实测确认）

BUG滚动导航漏掉「摄像头」章节

index.html 的 .scroll-rail 有 7 个锚点：sec-hero / ch-trigger / ch-voice / ch-softpad / sec-brands / sec-quotes / site-download-cta。

但页面实际定义了 4 个 story chapter：ch-trigger / ch-camera / ch-voice / ch-softpad。

→ #ch-camera 有章节、有内容、有计数器编号，却没有对应的导航点。右下角计数器显示「01 / 04」，而导航只跳 3 个章节，两者对不上。

修法：在 rail 里补一个 data-target="#ch-camera"，位置在 trigger 和 voice 之间。

BUGquickstart.html 与 keys.html 近乎重复

两页共享 18 个相同 id（qs-hero、neural-canvas、node-layer-keys、rn-*、hn-hub 等），hero 完全一样，<title> 也完全一样（都是「语音与按键 — 一声 OneTone」）。

→ 这是同一个页面的两个副本。后果：SEO 互相蚕食、改一处忘另一处、用户分不清该看哪个。

修法（三选一）：

  • 推荐：合并成 quickstart.html，keys 的内容作为其中一个 step；keys.html 做 301 跳转
  • 或：keys 专做「按键映射参考手册」，去掉 hero 和神经网 demo，走纯文档风
  • 最低成本：至少先把 <title> 改成「按键映射 — 一声 OneTone」，description 也区分开

BUG「假互动」：看起来能点，点了没用

index.html 的 .command-item（鼠标侧键 / 手柄 / 戒指 / 麦克风口令）是 4 个 <button>，视觉上完全可点。

但 js/home-demo.js 中没有任何 click 监听——它只是每 1800ms 自动轮播 is-active 类：

flowItems.forEach(item => item.classList.toggle("is-active", i === flowIndex)); … await ctx.sleep(1800);

整个 home-demo.js（27 KB）里 0 个 click 监听，11 处 setInterval/setTimeout。首页 <input> 数量为 0。

→ vibecoding 用户天生会去点、去试。点了没反应，是最伤信任的一类体验。

修法（成本从低到高）：

  • 低：给 4 个 button 加 click → 立刻切到对应项并暂停自动轮播，让用户有掌控感
  • 中：轮播第一次播完后停住，交还控制权（"演示一遍，然后你自己点"）
  • 高：做成一个真的可玩 demo——点「鼠标侧键」→ 出现"按住说话"按钮 → 用 Web Speech API 真的转写一段（浏览器原生，无需后端）

BUG3 个功能页没进主导航

所有 7 个页面的主导航完全一致：首页 / 上手 / 帮助（+ 右侧「下载」按钮）。

但网站有 4 个功能页：keys.html（按键）、vision.html（摄像头）、agent.html（SoftPad）、以及 quickstart。前 3 个只能从 footer 或正文内链进入。

→ 花了大力气做的功能页，用户从导航找不到。

修法：导航改成 首页 / 上手 / 功能▾ / 帮助 / 下载，下拉里放 语音 · 按键 · 摄像头 · SoftPad。同时把 header 的「下载」保留为独立高亮按钮。

偏差生产环境依赖 4 个外部 CDN

依赖出现次数问题
fonts.googleapis.com12国内不可靠，是首屏白屏/卡顿的主因之一
cdn.tailwindcss.com12Tailwind CDN 官方明确不建议上生产：全量 JS、运行时编译、FOUC
unpkg.com（Phosphor）13全量图标库，实际只用了几十个图标
cdn.jsdelivr.net（GSAP）7体积不小，且首页动效并非强依赖

实测：本地起服务打开 index.html，浏览器等待 load 事件超时——四个 CDN 串行拉取（各 2–4 秒）直接把首屏拖垮。而 WorkBuddy 作为 SPA 至少是打包自托管的。

修法（按性价比排序）：

  • 最高性价比：给 fonts.googleapis.com 加 media="print" onload="this.media='all'" 异步化，或直接换自托管/国内镜像（如 fonts.googleapis.cn、字节静态资源）。字体不该阻塞渲染。
  • 次高：把 Tailwind 在本地 build 成静态 CSS 产物提交（一次性工作，之后 all pages 受益）
  • Phosphor 图标：改成只打包用到的 SVG（或直接内联 symbol sprite）
  • GSAP：首页保留，其余页面按需加载

偏差i18n：673 vs 679，英文缺 8 个 key

中文 679 个 key，英文 673 个。切到 EN 时这 8 个会露馅：

qsStep1Title · qsStep1Desc · qsStep2Title · qsStep2Desc · qsStep3Title · qsStep3Desc · qsSuccessTitle · qsSuccessVerdict

这些恰好是快速上手三步的文案——也就是英文用户转化路径上最关键的一段。

另外 i18n.js 有 88 KB，全站每个页面都整包加载，而单个页面只用其中一小部分。

修法：先补齐这 8 个 key；中期考虑按页面拆分语言包。

偏差changelog.html 的 description 是废话

<meta name="description" content="更新日志 — 一声 OneTone"> —— 等于没写。

改成：一声 OneTone 的版本更新记录：新功能、问题修复与兼容性改进。

偏差CTA 按钮与品牌色脱节

.nav-cta 和 .site-download-cta-btn 都是白底黑字（background:#fff; color:#000），而品牌色是 cyan #2a9cc4。

WorkBuddy 的主 CTA 用的是品牌绿。OneTone 的 CTA 用了中性白，导致品牌识别被稀释——页面到处是青色发光，但最该被点的按钮反而是白的。

修法：把主 CTA 改成品牌青（background:var(--mac-accent)），次要按钮保持描边白。同时全局统一——现在 .nav-cta、.dl-primary-btn、.site-download-cta-btn 三套按钮样式各写各的。

4 · 审美与 UI

做得好的（别动）

  • ✓ 不是滚动劫持：.story-chapter 是 min-height:100vh 的自然滚动，没有 pin 牢用户——这比很多"创意官网"克制，很好。
  • ✓ 尊重 prefers-reduced-motion：site-scroll.js 和 home-gsap.js 都做了降级处理。
  • ✓ 深色 HUD 与开发者工具调性吻合——vibecoding 用户就是 Cursor/终端深色党，这个方向是对的。
  • ✓ 品牌兼容墙（"在哪写就在哪说"）方向正确，比硬套"客户墙"诚实。

建议调整的

问题现状建议
命名前缀混乱 至少 8 套前缀并存：mac-*（macOS 遗留）、site-*、qs-*、hct-*、pad-teaser-*、op-*、rn-*、dl-* 不用一次性重构，但新写的样式统一到 ot- 前缀，逐步收敛。mac- 前缀对一个 Windows 工具尤其违和。

信息密度被稀释 4 个章节每屏只有「1 个场景胶囊 + 1 个 eyebrow + 1 个问句 + 1 段回答 + 1 个 chip + 1 个 demo」 把「结果」前置：每个章节先给一句可验证的结果（如"按下侧键 → 8 秒后 52 个字进 Cursor"），再展开原理。

5 · 叙事：从"能力清单"改成"问题-解决"

现在的叙事主线是"我们有哪些能力"：

触发（我怎么开麦）→ 摄像头（体态也能开麦）→ 语音（说了字会跟上吗）→ SoftPad（有时你想叫它停）

建议改成 vibecoding 用户的真实困境：

手比脑子慢（说话比打字快 3 倍）→ 但我懒得找按钮（所以按一下侧键）→ 说错了想重来（Esc 取消）→ Agent 跑飞了想叫停（SoftPad）

两套叙事用的是同样的素材，差别只在主语：现在的主语是"产品功能"，建议改成"用户处境"。vibecoding 用户对"功能介绍"免疫，对"我也有这个问题"有反应。

具体改写示例

章节现在建议
ch-trigger 「我怎么开麦？」
绑一次外设，到处能说。侧键、手柄、戒指——顺手的动作就是你的开麦键。		 「手上有活，怎么开口？」
把开麦键绑到你已经在按的那个键上。侧键、手柄、戒指都行——不用抬手去找麦克风图标。
ch-voice 「说了，字会跟上吗？」
好的语音输入不该让你先停下来找按钮。		 「说完了，字在哪？」
字直接落在你正在打字的那个光标上。说错了按 Esc，这段清空重来。
ch-softpad 「有时你想叫它停？」
屏幕上的小键盘，可展开、可收成迷你栏。		 「Agent 跑偏了，怎么喊停？」
屏幕角落的迷你栏，数字键一对一接管你的 Agent——不用切窗口去点停止。

注：bridge 文案（"下面，麦到你手上了"）写得很好，保留，这是全站最有记忆点的部分。

6 · 帮 vibecoding 用户"理解 → 下载试用"

这是整个分析里最该优先做的一块。WorkBuddy 转化做得好，靠的是把用户的每一步疑虑提前消灭。

1

先回答"这跟我有什么关系"

vibecoding 用户的第一问不是"这是什么"，是"我在 Cursor / Claude Code 里能用吗"。

→ 把品牌兼容墙从页面中段提到 hero 正下方，并把文案从"在哪写就在哪说"改成"已在 Cursor / Claude / Trae / Windsurf 验证可用"。用"已验证"替代"支持"，可信度完全不同。

2

消灭"要花多少时间"的疑虑

WorkBuddy 用"15 分钟交付报告"设定预期。OneTone 现在完全没提时间成本。

→ hero 副标题直接写 3 分钟装好；download.html 的"装好了，下一步这样做"保留（这块做得很好）。

3

提前打 SmartScreen 预防针

现在 SmartScreen 说明只在 download.html。用户如果直接从 hero 的下载按钮跳走，安装时遇到拦截会以为中毒。

→ 在 hero 的下载按钮下方加一行小字：首次安装 Windows 会提示 SmartScreen，点「更多信息 → 仍要运行」即可 · 开源免签。download.html 里这段处理得很好，把它前置。

4

给一个"不用装也能信"的证据

vibecoding 用户习惯先验证再安装。

→ 三选一：GitHub star 数（如果拿得出手就直接放）、一段 15 秒真机录屏（比 SVG demo 可信）、或社区讨论截图。现有的 8 条多语言评价很棒，但都是"语音输入"的价值，不是"一声"的价值——建议补 1–2 条明确提到"用一声之后"的评价。

5

把"下载"做成常驻而非终点

现在 header 的下载按钮是 position:fixed 常驻的，这点做得对。

→ 补两点：滚动超过 1 屏后，header 下载按钮收窄成小胶囊并显示体积（下载 · 30 MB）；每个章节末尾加章节级下载链接。

8 · 一句话总结

跟 WorkBuddy 学"怎么说"，不学"摆什么"。

学它的一句话价值、把真产品摆上首屏、用数字设定预期；不要学它的定价表、客户 logo 墙、生态背书——那些是腾讯规模才撑得起来的，独立开源项目照抄会露怯。

而 OneTone 真正该优先补的，不是新的动效，是4 个已经存在的 bug（漏锚点、缺英文 key、标题重复、字体阻塞）和3 个说服力缺口（没有数字、假互动、没有"我的场景能用吗"的答案）。
